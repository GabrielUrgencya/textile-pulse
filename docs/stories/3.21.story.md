# Story 3.21 — Permission Checks em Rotas de Escrita + DialogDescription

## Status: Ready for Review

## Story

Como equipe de segurança, precisamos que rotas de escrita críticas (defects, production orders) tenham verificação de permissão via `hasPermission()`, e que todos os modais Dialog tenham `DialogDescription` para conformidade com acessibilidade Radix UI.

## Origin

- Auditoria @qa: 4 MEDIUM (missing permission checks) + 3 MEDIUM (missing DialogDescription)
- Plano @architect: usar permissões existentes em permissions.ts + adicionar DialogDescription

## Acceptance Criteria

### AC1: Permission checks em 4 rotas de escrita
- **Given** 4 rotas de escrita permitem qualquer usuário autenticado executar operações
- **When** permission checks são adicionados
- **Then** cada rota verifica a permissão antes de executar a operação
- **And** retorna 403 com mensagem clara se não autorizado

Rotas e permissões:
1. `src/app/api/defects/route.ts` POST — `quality:manage` (ADMIN, GERENTE têm)
2. `src/app/api/defects/[id]/resolve/route.ts` POST — `quality:manage`
3. `src/app/api/production/orders/[id]/route.ts` PATCH — `orders:edit` (ADMIN, GERENTE têm)
4. `src/app/api/production/orders/[id]/lots/route.ts` POST — `orders:create` (ADMIN, GERENTE, COORDENADOR têm)

NOTA: Todas essas permissões JÁ EXISTEM em `src/lib/permissions.ts`. Mas a rota `defects/route.ts` POST precisa considerar que COORDENADOR também tem `quality:manage`? NÃO — verificar a tabela: COORDENADOR NÃO tem `quality:manage`. Apenas ADMIN e GERENTE. Isso é correto: operadores reportam defeitos via rework, não diretamente.

CORREÇÃO: Na verdade, qualquer operador pode reportar defeito pelo fluxo de scan. A rota `defects/route.ts` POST é chamada pelo componente de reportar defeito na tela de scan. Portanto, a permissão correta é `rework:report` (que OPERADOR, COORDENADOR, GERENTE e ADMIN têm).

Permissões finais:
1. `defects/route.ts` POST — `rework:report`
2. `defects/[id]/resolve/route.ts` POST — `rework:resolve` (COORDENADOR+)
3. `production/orders/[id]/route.ts` PATCH — `orders:edit`
4. `production/orders/[id]/lots/route.ts` POST — `orders:create`

### AC2: DialogDescription em 3 componentes
- **Given** 3 componentes usam `DialogContent` sem `DialogDescription`
- **When** `DialogDescription` é adicionado
- **Then** cada modal tem texto descritivo contextual
- **And** o warning `Missing Description or aria-describedby` desaparece

Componentes:
1. `src/components/settings/TokenManager.tsx` — "Gerencie tokens de acesso."
2. `src/components/factions/ShipmentCreate.tsx` — "Crie uma nova remessa para a facção."
3. `src/components/factions/ShipmentReceive.tsx` — "Registre o recebimento da remessa."

### AC3: Validação
- `tsc --noEmit` passa limpo
- `next lint` passa limpo

## Complexity: S

## Dev Notes

### Padrão permission check:
```typescript
import { hasPermission, type AppRole } from "@/lib/permissions";

const role = user.app_metadata?.role;
if (!hasPermission(role as AppRole, "quality:manage")) {
  return NextResponse.json({ error: "Forbidden: quality:manage required" }, { status: 403 });
}
```

### Padrão DialogDescription:
```tsx
import { DialogDescription } from "@/components/ui/dialog";

// Dentro do DialogHeader, após DialogTitle:
<DialogDescription>Texto descritivo.</DialogDescription>
```
