## Descricao

Como sistema, preciso que as tabelas `faction_shipments`, `defect_records` e `notifications` tenham campos adicionais para suportar confirmacao de recebimento pela faccao, contestacao de defeitos, reagendamentos e notificacoes direcionadas a faccoes.

## Criterios de Aceitacao

- [x] **AC1:** Migration adiciona 5 campos em `faction_shipments`: `faction_confirmed_at`, `faction_estimated_return`, `faction_estimated_return_at`, `reschedule_count` (default 0), `last_rescheduled_at`
- [x] **AC2:** Migration adiciona 4 campos em `defect_records`: `faction_response` (ENUM: CONFIRMED/CONTESTED), `faction_response_at`, `contestation_reason`, `contestation_resolved_at`
- [x] **AC3:** Migration adiciona 1 campo em `notifications`: `faction_id` (UUID nullable, FK para factions)
- [x] **AC4:** Modelos Prisma atualizados com todos os novos campos e relations
- [x] **AC5:** Migration e reversivel (DOWN migration remove campos)
- [x] **AC6:** Build e typecheck passam apos alteracoes

## Notas Tecnicas

- **`faction_response` CHECK constraint:** `CHECK (faction_response IN ('CONFIRMED', 'CONTESTED'))` — nao usar ENUM do Postgres, usar CHECK para simplificar
- **`reschedule_count` default 0:** Importante para queries de limite (R3)
- **`faction_id` nullable:** Campo opcional em notifications — nao quebra notificacoes existentes
- **Source:** `docs/architecture/FACTION-PORTAL-ARCHITECTURE.md` secao 3
