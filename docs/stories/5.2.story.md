## Notas Tecnicas

- **Item 1 (v2.1) — CRITICO:** Policy `scan_insert` atual nao valida tenant. Reescrever com JOIN chain:
  ```sql
  CREATE POLICY "scan_insert" ON scan_events
    FOR INSERT WITH CHECK (
      EXISTS (
        SELECT 1 FROM lots l
        JOIN production_orders po ON po.id = l.po_id
        WHERE l.id = lot_id
          AND po.tenant_id = auth_tenant_id()
      )
      AND user_id = auth.uid()
    );
  ```
- **Funcao helper:** `auth_tenant_id()` extrai `tenant_id` do JWT claim customizado do Supabase Auth
- **Padrao de policies:** Cada tabela deve ter policies para SELECT, INSERT, UPDATE, DELETE conforme necessidade
- **Performance:** JOINs nas policies sao aceitaveis para volume do piloto (<500 lotes/mes)
- **Recomendacao PO:** RLS policies devem ser incluidas como raw SQL dentro das Prisma migrations para manter versionamento unico
- **Source:** `docs/architecture/ARCHITECTURE-REVIEW-v2.1.md` item 1

## Dev Agent Record

### Debug Log References
- `prisma migrate dev` falha com shadow database (schema `auth` nao existe no shadow). Solucao: `prisma db execute` + `prisma migrate resolve --applied`
- `auth_tenant_id()` busca tenant_id em `app_metadata` primeiro, fallback para `user_metadata` (compatível com diferentes configs de Supabase Auth)
- Tabelas sem `tenant_id` direto usam cadeia de JOINs: lots→po, scan_events→lots→po, defect_records→lots→po, aduana_validations→lots→po, faction_shipments→factions, ops_clock→drivers

### Completion Notes

- Padrão de policies: SELECT + INSERT + UPDATE (DELETE não incluído — soft delete via `deleted_at`)
- `scan_events_insert` valida cadeia completa + `user_id = auth.uid()` (Item 1 v2.1)
- `defect_records_insert` valida cadeia + `detected_by = auth.uid()`

- `tenants` somente SELECT (tenant não se auto-modifica via RLS)
