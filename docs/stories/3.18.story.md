## Descricao

Como administrador do LISION, preciso que o sistema de permissions seja efetivamente integrado nas API routes (nao apenas criado e ignorado), que os endpoints sigam o contrato de API padrao, e que inputs sejam validados adequadamente — para garantir seguranca, consistencia e previsibilidade da plataforma.

**Contexto:** A review de QA (docs/qa/QA_FIX_REQUEST.md) identificou que `src/lib/permissions.ts` foi criado com funcoes `hasPermission()`, `hasMinRole()`, etc., mas NENHUMA API route o utiliza. Todas fazem checks hardcoded `if (!["ADMIN", "GERENTE"].includes(role))`. Alem disso, a Profile API viola o contrato de response, Team POST nao valida role, Stages POST nao valida nome unico, e search parameters sao vulneraveis a wildcard injection.

## Criterios de Aceitacao

- [ ] **AC1 — Permissions integradas em TODAS as API routes (H3):** Todos os checks de autorizacao em `src/app/api/**/*.ts` usam funcoes de `src/lib/permissions.ts` (`hasPermission()`, `hasMinRole()`, ou `hasAnyPermission()`). ZERO ocorrencias de `["ADMIN", "GERENTE"].includes(role)` ou pattern similar hardcoded. Cada route declara a permission necessaria (ex: `hasMinRole(role, "GERENTE")` ou `hasPermission(role, "factions:manage")`). `grep -r 'includes(role)' src/app/api/` retorna 0 resultados.

- [ ] **AC2 — Profile API segue contrato (M1):** `GET /api/profile` e `PATCH /api/profile` retornam `{ data: ... }` ao inves de `{ profile: ... }`. Frontend que consome este endpoint (`use-user-profile.ts` ou similar) atualizado para ler `response.data`. Erro retorna `{ error: "mensagem" }`. Contrato alinhado com gap analysis secao 5.3.

- [ ] **AC3 — Team POST valida role (M4):** `POST /api/team/members` valida que o campo `role` e um dos valores permitidos: `ADMIN`, `GERENTE`, `COORDENADOR`, `OPERADOR`. Dado POST com `role: "HACKER"`, retorna HTTP 400 com `{ error: "Role invalido. Valores permitidos: ADMIN, GERENTE, COORDENADOR, OPERADOR" }`. Dado POST com `role: "OPERADOR"`, criacao procede normalmente.

- [ ] **AC4 — Stages POST valida nome unico (M5):** `POST /api/settings/stages` verifica se ja existe stage com mesmo `name` no `tenant_id` antes de inserir. Dado stage "Corte" ja existe no tenant, quando POST com `name: "Corte"`, retorna HTTP 409 com `{ error: "Stage com este nome ja existe" }`. Comparacao case-insensitive (CORTE == corte == Corte).

- [ ] **AC5 — Search escapado contra wildcard (M6):** Todos os endpoints que usam `.ilike()` com parametro `search` do usuario escapam caracteres `%` e `_` antes de construir o pattern. Criar funcao utilitaria `escapeLikePattern(search: string): string` em `src/lib/utils.ts` ou similar. Dado busca com `search=100%`, query busca literal "100%", nao "100" seguido de wildcard. Dado busca com `search=test_user`, busca literal "test_user".

- [ ] **AC6 — Build e typecheck passam:** `tsc --noEmit` + `next build` sem erros.

### H3 — Padrao de integracao de permissions

```typescript
// ANTES (ruim)
if (!["ADMIN", "GERENTE"].includes(role)) {
  return NextResponse.json({ error: "Forbidden" }, { status: 403 });
}

// DEPOIS (bom)
import { hasMinRole } from "@/lib/permissions";

if (!hasMinRole(role, "GERENTE")) {
  return NextResponse.json({ error: "Sem permissao" }, { status: 403 });
}
```

### M6 — Funcao utilitaria

```typescript
// src/lib/utils.ts
export function escapeLikePattern(input: string): string {
  return input.replace(/%/g, "\\%").replace(/_/g, "\\_");
}
```
