## Descricao

Como administrador do LISION, preciso que os endpoints de qualidade, reordenacao de stages e notificacoes sejam seguros e performaticos — quality overview nao deve carregar todos os registros em memoria, reordenacao de stages deve ser atomica (transacional), mark-all-read de notificacoes nao deve afetar outros usuarios, e erros de query nao devem ser engolidos silenciosamente — para garantir estabilidade, seguranca e escalabilidade do sistema.

**Contexto:** A review de QA (docs/qa/QA_FIX_REQUEST.md) identificou 4 bugs HIGH: (1) quality overview busca todos os defect_records em memoria JS para contar, (2) reorder de stages faz N+1 queries sem transaction, (3) mark-all-read de notificacoes pode marcar broadcasts de outros usuarios como lidos, (4) quality/by-faction retorna 200 com data vazio quando query falha.

## Criterios de Aceitacao

- [ ] **AC1 — Quality overview com COUNT SQL (H1):** `GET /api/quality/overview` usa queries SQL agregadas (COUNT com GROUP BY) ao inves de buscar todos os registros em memoria. A response mantem o mesmo formato de antes. Nenhum `select("*")` seguido de `.filter().length` em JS. Tempo de resposta < 500ms com 10k+ registros no banco.

- [ ] **AC2 — Stages reorder atomico (H2):** `POST /api/settings/stages/reorder` executa todas as atualizacoes de order_index em uma unica operacao atomica. Opcoes: (a) RPC/stored procedure que recebe array e faz UPDATE em batch dentro de transaction, OU (b) usar `Promise.all()` se Supabase RLS garante atomicidade, mas PREFERENCIALMENTE RPC. Se qualquer update falhar, NENHUMA ordem e alterada (rollback). Dado 10 stages reordenados, apenas 1 round-trip ao banco.

- [ ] **AC3 — Notifications mark-all-read seguro (H4):** `POST /api/notifications/read` (mark-all) adiciona filtro explicito por usuario: apenas notificacoes onde `user_id = currentUserId` OU notificacoes broadcast que ainda nao foram marcadas como lidas PELO USUARIO ATUAL (nao por qualquer usuario). Se necessario, criar tabela `notification_reads(user_id, notification_id, read_at)` para rastrear leitura individual de broadcasts. Dado usuario A marca todas como lidas, as notificacoes broadcast do usuario B permanecem nao-lidas.

- [ ] **AC4 — Quality by-faction retorna erro real (H5):** `GET /api/quality/by-faction` retorna HTTP 500 com `{ error: "mensagem" }` quando query falha, ao inves de HTTP 200 com `{ data: [] }`. Adiciona `console.error("[quality/by-faction]", error)` para log server-side. Frontend que consome este endpoint trata o erro adequadamente (mostra toast ou empty state com mensagem de erro).

- [ ] **AC5 — Build e typecheck passam:** `tsc --noEmit` + `next build` sem erros.

### H1 — Exemplo de query agregada

```typescript
// ANTES (ruim): busca tudo em memoria
const { data: records } = await supabase.from("defect_records").select("*");
const critical = records.filter(r => r.severity === "CRITICAL").length;

// DEPOIS (bom): COUNT no SQL
const { count: critical } = await supabase
  .from("defect_records")
  .select("id", { count: "exact", head: true })
  .eq("severity", "CRITICAL");
```

### H2 — Exemplo de RPC

```sql
-- Migration: supabase/migrations/reorder_stages.sql
CREATE OR REPLACE FUNCTION reorder_stages(updates jsonb)
RETURNS void AS $$
BEGIN
  FOR i IN 0..jsonb_array_length(updates)-1 LOOP
    UPDATE stages
    SET order_index = (updates->i->>'order_index')::int
    WHERE id = (updates->i->>'id')::uuid;
  END LOOP;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```
