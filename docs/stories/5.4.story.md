## Descricao

Como operador de chao de fabrica, preciso bipar lotes com scanner USB para registrar a passagem por cada estagio de producao, atualizando o status do lote e criando eventos de scan rastreraveis.

## Criterios de Aceitacao

- [x] **AC1:** Endpoint `POST /api/scan` recebe `{ barcode, stage_id }` e cria `scan_event`
- [x] **AC2:** Barcode validado contra formato `^OP-[0-9]{8}-[0-9]{3}-L[0-9]{3}$`
- [x] **AC3:** Status do lote atualizado automaticamente para o estagio correspondente
- [x] **AC4:** Scan duplicado (mesmo lote, mesmo estagio) rejeitado com erro descritivo
- [x] **AC5:** `scan_event` registra: `lot_id`, `stage_id`, `user_id`, `scanned_at`, `device_info`
- [x] **AC6:** Endpoint `GET /api/scan/history/:lotId` retorna historico de scans do lote
- [x] **AC7:** Todas as queries usam Supabase client autenticado (NAO Prisma)
- [x] **AC8:** RLS garante que operador so cria scans para lotes do seu tenant

## Escopo

**IN:**
- Endpoint POST /api/scan (criar scan event)
- Endpoint GET /api/scan/history/[lotId] (historico)
- Validacao de barcode
- Atualizacao de status do lote
- Protecao contra scan duplicado

**OUT:**
- Sync offline de scans (Item 15 v2.1 — Fase 2)

## Notas Tecnicas

- **Fluxo de bipagem:**
  1. Scanner USB envia barcode como input de teclado
  2. Frontend captura e envia POST /api/scan
  3. Backend valida barcode, verifica lote existe, verifica stage valido
  4. Cria scan_event, atualiza lot.current_stage_id e lot.status
  5. Retorna scan_event criado
- **Validacao de sequencia:** Na Fase 1, alertar mas nao bloquear scans fora de ordem (operacao da fabrica nao pode parar)
- **Quantidades computadas:** NAO atualizar campos de quantidade em production_orders (removidos no Item 5). Dashboard computa via query.
- **Source:** `docs/architecture/ARCHITECTURE-REVIEW-v2.1.md` item 5 (Opcao A)
