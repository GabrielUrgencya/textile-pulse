## Descrição

Como gerente, preciso imprimir etiquetas com código de barras para cada sub-lote, compatíveis com a impressora Zebra GC420t via ZPL, para identificar fisicamente os lotes na fábrica.

## Critérios de Aceitação

- [ ] **AC1:** Botão "Imprimir Etiquetas" na tela de detalhes da OP (`/production/orders/[id]`), visível para roles com permissão `labels:print` (ADMIN, GERENTE, COORDENADOR)
- [ ] **AC2:** Gera ZPL válido via API existente `POST /api/print/label` com `{ lot_ids }`. API já implementada em Story 5.6
- [ ] **AC3:** Opção de imprimir etiqueta individual (1 lote — checkbox) ou em lote (botão "Selecionar Todos" + "Imprimir Selecionados")
- [ ] **AC4:** Preview visual da etiqueta na tela antes de download (representação HTML/CSS do layout: barcode, OP, lote, produto, referência)
- [ ] **AC5:** Download do arquivo ZPL para o operador enviar à impressora. Botão alternativo "Baixar PDF" que chama a API com `?format=pdf`
- [ ] **AC6:** Feedback visual: toast de sucesso após download, toast de erro se API falhar. Loading state durante chamada à API

## Escopo

**IN:**
- Botão "Imprimir Etiquetas" na tela de detalhes da OP
- Seleção individual e em lote de sub-lotes para impressão
- Preview visual da etiqueta (HTML/CSS, não ZPL renderizado)
- Download de arquivo ZPL (padrão) ou PDF (fallback)
- Chamada à API existente `POST /api/print/label` (Story 5.6 — Done, NÃO MODIFICAR a API)
- Correção da API para usar `withAuth()` em vez de `getUser()` (performance fix)

**OUT:**
- Envio direto para impressora via raw printing (Fase 2 — requer BrowserPrint SDK ou daemon local)
- Configuração de template de etiqueta pelo usuário (fixo na Fase 1)
- Suporte a outras impressoras além da Zebra GC420t
- Reimpressão com controle de duplicatas
- QR Code (apenas Code128 na Fase 1)
- Tabela `label_prints` para registro de impressões (Fase 2 — requer migration)

## Riscos

| Risco | Impacto | Mitigação |
|-------|---------|-----------|
| Preview visual não corresponde à etiqueta real | Operador imprime etiqueta errada | Preview mostra mesmos dados que o ZPL, com aviso "Representação aproximada" |
| Download de ZPL pode ser bloqueado pelo browser | Operador não consegue baixar | Usar `application/octet-stream` + `Content-Disposition: attachment` (já configurado na API) |
| Muitos lotes selecionados trava a API | UX degradada | API já tem limite de 50 labels por request — respeitar no frontend |
| `jsPDF` + `bwip-js` aumentam bundle size | Performance impactada | API faz dynamic import, não afeta bundle do frontend |

### REGRA OBRIGATÓRIA — Design Guidelines

**TODAS as telas e componentes visuais DEVEM seguir `docs/ux/FRONTEND-DESIGN-GUIDELINES.md`.**

### API Backend Existente — POST /api/print/label

**Arquivo:** `src/app/api/print/label/route.ts` (Story 5.6 — DONE)

**Payload:**
```json
{
  "lot_ids": ["uuid-1", "uuid-2", "uuid-3"]
}
```

**Query params:**
- `?format=pdf` — retorna PDF em vez de ZPL

**Respostas:**
| Status | Significado | Body |
|--------|-------------|------|
| `200` | Sucesso ZPL | `application/octet-stream` (arquivo ZPL) |
| `200` | Sucesso PDF | `application/pdf` (arquivo PDF) |
| `400` | `lot_ids` inválido | `{ error: "lot_ids array is required..." }` |
| `401` | Não autenticado | `{ error: "Unauthorized" }` |
| `403` | Lotes de outro tenant | `{ error: "Some lots not found...", missing_lot_ids }` |
| `404` | Nenhum lote encontrado | `{ error: "No lots found..." }` |

**Limite:** Máximo 50 labels por request (`MAX_LABELS = 50`)

**Dados disponíveis por lote:** `barcode`, `op_number`, `lot_number`, `product_name`, `reference`
