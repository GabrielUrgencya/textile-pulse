## Descricao

Como gerente do LISION, preciso que os dados exibidos no modulo de faccoes sejam REAIS e nao fabricados — defeitos filtrados por faccao (nao aleatorios do tenant), valores financeiros calculados (nao hardcoded zero), e KPIs agregados reais (nao falsos) — para que eu possa tomar decisoes de negocio com dados corretos e nao haja vazamento de informacao entre faccoes.

**Contexto:** A review de QA (docs/qa/QA_FIX_REQUEST.md) identificou 3 bugs CRITICAL no modulo de faccoes: (1) query de defeitos sem filtro faction_id expoe dados entre faccoes, (2) secao financeira retorna zeros hardcoded, (3) KPIs avgDefectRate e totalPendingValue hardcoded a zero. Adicionalmente, o FactionScoreCard tem props desalinhadas com a spec UX (recebe rating/totalPieces ao inves de deliveryScore/qualityScore/volumeTotal).

## Criterios de Aceitacao

- [ ] **AC1 — Defeitos filtrados por faccao (C1):** GET `/api/factions/[id]` retorna APENAS defeitos associados a lotes que foram enviados para a faccao especifica via shipments. A query deve fazer join: `defect_records` -> `lots` -> `shipment_lots` -> `shipments` WHERE `shipments.faction_id = id`. Se `defect_records` tiver coluna `faction_id` diretamente, usar `.eq("faction_id", id)`. Dado faccao A com 3 defeitos e faccao B com 5 defeitos, quando GET `/api/factions/A`, entao retorna apenas os 3 defeitos de A. Zero defeitos de B aparecem.

- [ ] **AC2 — Financial calculado (C2):** GET `/api/factions/[id]` retorna `financial.grossValue` calculado como SUM(pecas * preco_por_peca) dos lotes da faccao no periodo. `financial.deductions` como SUM de deducoes por defeitos ou atrasos (se nao houver logica de deducao definida, retornar 0 com comentario TODO). `financial.netValue` = grossValue - deductions. O frontend `FactionDetail.tsx` renderiza os valores reais formatados em BRL. Dado faccao com 500 pecas a R$4,50/peca, quando detalhe carrega, entao exibe R$ 2.250,00 como valor bruto.

- [ ] **AC3 — KPIs reais no listing (C3):** GET `/api/factions` retorna `kpis.avgDefectRate` calculado como media ponderada da taxa de defeitos por faccao ativa (total_defeitos / total_pecas_enviadas * 100). `kpis.totalPendingValue` calculado como SUM de valores de remessas com status != PAID (ou remessas completadas sem pagamento registrado). Dado 3 faccoes com taxas 2%, 5%, 3%, quando GET `/api/factions`, entao avgDefectRate ~= 3.33. Dado R$5000 pendente, totalPendingValue = 5000.

- [ ] **AC4 — FactionScoreCard alinhado com UX (UX1):** Componente FactionScoreCard refatorado para aceitar props: `deliveryScore` (% pontualidade), `qualityScore` (% qualidade), `volumeTotal` (total pecas processadas). API `/api/factions/[id]` retorna estes 3 scores calculados. O card exibe 3 metricas separadas conforme wireframe da secao 2.2 do UX-FRONTEND-ARCHITECTURE.md. Score de entrega = remessas devolvidas no prazo / total remessas * 100. Score de qualidade = (1 - defeitos / total_pecas) * 100. Volume = SUM pecas de todas as remessas.

- [ ] **AC5 — Build e typecheck passam:** `tsc --noEmit` + `next build` sem erros.
