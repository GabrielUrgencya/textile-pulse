## Descrição

Hoje a Karen monta um plano de produção por dia e **manda por mensagem** para a gerente (Andiara):
> Segunda: 1001 completo + 1053 + 2 cores do 1004 (meta 181,6)
> Terça: resto do 1004 + 9000 + 1 tamanho do 1002 Pantera (179,2)

Esta story leva esse plano para dentro do sistema: a Karen **monta o plano do dia** (itens estruturados) e a gerente/operador **vê no Dashboard** um card **"Hoje você precisa produzir"** — sem depender de mensagem.

> Fundação de dados já aplicada (Dara): `daily_plans` (1 por tenant/data, `target_override`, notes) e `daily_plan_items` (reference, color, size_label, quantity, meta_value, sort_order), RLS tenant-scoped via `auth_tenant_id()`. Models `DailyPlan`/`DailyPlanItem` no schema.

## Critérios de Aceitação

### A — API do plano por data
- [x] **AC1:** **Given** o endpoint `GET /api/production/daily-plan?date=YYYY-MM-DD`, **When** chamado, **Then** retorna o plano daquela data (ou vazio se não existir) com seus itens ordenados por `sort_order` e a **meta do dia calculada** (= `target_override` se houver, senão Σ `meta_value` dos itens).
- [x] **AC2:** **Given** `POST/PUT /api/production/daily-plan` com `{ date, items: [...], target_override? , notes? }` e permissão `settings:manage`, **When** salvo, **Then** o plano da data é criado/atualizado (upsert por `tenant+data`) e os itens são substituídos pelo conjunto enviado (replace transacional).
- [x] **AC3:** **Given** um usuário **sem** `settings:manage`, **When** tenta `POST/PUT`, **Then** recebe `403` (somente leitura via GET).
- [x] **AC4:** **Given** `meta_value` não informado em um item mas com `reference` + `quantity`, **When** salvo, **Then** o backend calcula `meta_value = quantity × meta_coefficient` da referência (de `reference_targets`; coeficiente 1.0 se a referência não estiver cadastrada). Valor continua **editável** (se enviado, prevalece).
- [x] **AC5:** **Given** RLS por tenant, **When** qualquer operação ocorre, **Then** só enxerga/edita planos do próprio tenant.

### B — Editor do plano (admin/gerente)
- [x] **AC6:** **Given** a tela do plano (aba/admin), **When** a Karen escolhe uma data, **Then** vê o plano existente (ou em branco) e pode **adicionar/editar/remover itens** (referência + cor + tamanho/escopo + quantidade), com a meta do dia somando automaticamente.
- [x] **AC7:** **Given** o campo de referência, **When** ela digita, **Then** há autofill/sugestão das referências cadastradas (como em "Nova OP", `datalist` de `/api/settings/references`).
- [x] **AC8:** **Given** a meta calculada, **When** ela quer um valor fixo, **Then** pode informar um **override** da meta do dia (campo editável); limpar o override volta para a soma automática.

### C — Card no Dashboard
- [x] **AC9:** **Given** o Dashboard (`src/components/dashboard/Dashboard.tsx`), **When** a gerente/operador abre, **Then** vê um card **"Hoje você precisa produzir"** listando os itens do plano de hoje (referência · cor · tamanho · quantidade) e a **meta do dia**.
- [x] **AC10:** **Given** que não há plano para hoje, **When** o card é exibido, **Then** mostra um estado vazio claro ("Nenhum plano definido para hoje") — sem erro.

## Notas Técnicas

- **Cálculo de meta:** seguir o padrão do `meta_coefficient` (8.13). `reference_targets` acessível via `/api/settings/references`. Coeficiente default 1.0 quando a referência não existe.
- **Replace transacional de itens:** ao salvar, apagar itens antigos do plano e inserir os novos (ou diferencial) — manter consistência; envolver em operação única.
- **Fuso horário:** "hoje" deve respeitar o timezone do tenant (settings `timezone`, default America/Sao_Paulo) para não trocar de dia à meia-noite UTC.
- **Permissão:** escrita com `can(user, "settings:manage")`; leitura (GET / card) liberada a usuários autenticados.
- **UI:** reutilizar `LisionCard`, `Field`, `input-field` e o padrão de `datalist` da tela "Nova OP".
- **Dashboard:** inserir o card sem quebrar o layout atual; estado vazio amigável.

### Observações (advisory, não bloqueiam)
1. **[MEDIUM]** **Replace de itens não-transacional** (`delete` + `insert` via supabase-js, sem transação real). Se o `insert` falhar após o `delete`, os itens daquele dia podem ficar vazios até novo salvamento — o plano (cabeçalho) persiste. Risco baixo na prática (payload pequeno, single-user admin). Mitigação futura: RPC/transação no Postgres.
2. **[LOW]** `daily_plans.updated_at` não é atualizado no UPDATE via supabase-js (o `@updatedAt` do Prisma não roda fora do client). Cosmético; se relevante, adicionar trigger `set updated_at = now()`.
3. **[LOW]** Sem teste automatizado do cálculo de meta — registrar como débito quando houver harness.
