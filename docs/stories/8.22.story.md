## Descrição

Hoje as permissões são uma tabela **fixa no código** (`src/lib/permissions.ts`, `ROLE_PERMISSIONS`), lida em 44 arquivos. O ADM precisa **editar pela plataforma** o que cada cargo (Gerente/Coordenador/Operador) pode **ver** (menus/telas) e **fazer** (ações nas APIs), sem mexer no código.

Decisões do dono: nível **por cargo**; profundidade **completa (ver + fazer)**.

## Arquitetura

- **Defaults = código:** o `ROLE_PERMISSIONS` atual permanece como **padrão/seed** (fonte de verdade inicial e fallback).
- **Overrides = banco:** tabela `role_permissions(tenant_id, role, permission, allowed)` guarda apenas as exceções editadas pelo ADM.
- **Efetivo = default ⊕ override:** `allowed=true` adiciona, `allowed=false` remove. Sem linha → usa o default.
- **Motor dinâmico:** `withAuth()` carrega as permissões efetivas do tenant+cargo (cache em memória, TTL curto, invalidado ao salvar) e expõe `can(permission)`. As 44 rotas passam a usar `auth.can("x")` no lugar de `hasPermission(role,"x")`.
- **Visibilidade:** cada item de menu/tela é mapeado a uma permissão; o `AppSidebar` filtra pelos `can` do usuário. Frontend recebe as permissões efetivas via `/api/me/permissions` (ou no `/api/profile`).

## Critérios de Aceitação

**Motor e dados:**
- [x] **AC1:** Tabela `role_permissions` (UNIQUE tenant_id+role+permission) com RLS: SELECT tenant-scoped (qualquer usuário do tenant lê), escrita gated admin na API
- [x] **AC2:** `getEffectivePermissions(tenant, role)` = defaults do cargo aplicando overrides (true adiciona / false remove); sem override usa default
- [x] **AC3:** Cache em memória por tenant com invalidação ao salvar (mudança reflete em ≤ TTL)
- [x] **AC4:** `withAuth()` expõe `can(permission)`; as 44 rotas usam o check dinâmico (nenhuma regressão de gate)

**Editor (admin):**
- [x] **AC5:** Aba "Permissões" (admin-only) com matriz cargo × permissão (liga/desliga), agrupada por módulo
- [x] **AC6:** Salvar grava override; "resetar" remove override (volta ao default)
- [x] **AC7:** `GET/PUT /api/settings/permissions` — leitura da matriz efetiva + escrita de override, gated por permissão admin

**Visibilidade:**
- [x] **AC8:** Itens do menu lateral e acesso às telas respeitam as permissões efetivas do usuário
- [x] **AC9:** Frontend obtém as permissões efetivas (endpoint `/api/me/permissions`) e gera o menu dinamicamente

**Segurança (guard rails):**
- [x] **AC10:** ADMIN nunca perde as permissões críticas (ex: `settings:manage`, `users:manage`, gerir permissões) — bloqueado na API (anti-lockout)
- [x] **AC11:** Edição de permissões restrita a ADMIN
- [x] **AC12:** `lint`, `tsc`, `build` passam

## Notas Técnicas / Riscos

- **Segurança-crítica:** refatorar autorização exige cuidado — validar que cada rota refatorada mantém o mesmo gate (mapa default = comportamento atual). Build + revisão obrigatórios.
- **Cache:** TTL ~30s; invalidar no PUT/DELETE (limpar entrada do tenant) para refletir rápido. JWT NÃO carrega permissões (evita exigir relogin).
- **Defaults imutáveis no código:** mantêm o sistema seguro mesmo com banco vazio.
- **Mapa menu→permissão:** Dashboard→dashboard:view, Produção→orders:view, Scan→scan:view, Qualidade→quality:view, Facções→factions:view, Equipe→users:manage, Configurações→settings:manage, etc. (definir no dev).
