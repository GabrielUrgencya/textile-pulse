## Descrição

**Bug:** Ao editar metas em Configurações (ex: "Meta diária de peças" 500→180) e salvar, o valor **não persiste** — ao recarregar volta ao padrão.

**Causa-raiz (confirmada):** A tabela `tenants` tem RLS habilitado com **apenas a policy `tenants_select`** (leitura). **Não existe policy de UPDATE.** O `PATCH /api/settings/targets` usa o client da sessão do usuário; o `UPDATE` em `tenants` é **bloqueado silenciosamente pelo RLS** (0 linhas afetadas, sem erro) → a API responde sucesso mas nada grava. Afeta TODAS as edições de configuração do tenant (metas, turnos, weighted meta, etc.).

## Critérios de Aceitação

- [ ] **AC1:** Existe policy de UPDATE em `tenants` permitindo atualização do próprio tenant (`id = auth_tenant_id()`)
- [ ] **AC2:** Given admin edita "Meta diária de peças" e salva, When recarrega Configurações, Then o valor persiste (não volta ao padrão)
- [ ] **AC3:** Isolamento mantido — um tenant não consegue atualizar settings de outro (WITH CHECK `id = auth_tenant_id()`)
- [ ] **AC4:** Edição continua restrita a admin na camada de API (`settings:manage` já valida) — sem regressão
- [ ] **AC5:** Smoke test: UPDATE de settings retorna linha afetada (não 0 linhas)

## Escopo

**IN:**
- Migration: `CREATE POLICY "tenants_update" ON tenants FOR UPDATE USING (id = auth_tenant_id()) WITH CHECK (id = auth_tenant_id());`
- Aplicar no banco remoto + registrar em `_prisma_migrations`

**OUT:**
- Reformulação da meta (Story 8.21)
- Mudança no código da API (a API já está correta; o bug é DB)

## Notas Técnicas

- A permissão admin já é validada na API (`hasPermission(role,'settings:manage')`), então a policy tenant-scoped é suficiente (defesa em profundidade pela API). Opcional: restringir a policy a role ADMIN via claim do JWT, com cautela para não quebrar caso o claim difira.
- Idempotente: `DROP POLICY IF EXISTS "tenants_update" ON tenants;` antes do CREATE.
