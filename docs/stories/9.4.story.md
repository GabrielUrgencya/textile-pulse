## Descrição

Hoje **qualquer colaborador consegue bipar em qualquer setor** — `/api/scan` só valida autenticação, rate limit e existência do código/etapa; **não há vínculo usuário→setor aplicado**. O gerente/ADM precisa poder **definir o que cada pessoa faz (setor)** e o sistema deve **impedir bipagem fora do setor atribuído**.

## Critérios de Aceitação

- [ ] **AC1:** **Given** um ADM/gerente com `settings:manage`/`users:manage`, **When** abre a gestão de equipe, **Then** consegue **atribuir o setor** (etapa) de cada colaborador.
- [ ] **AC2:** **Given** um operador atribuído ao setor X, **When** tenta bipar (`STAGE_IN` ou `STAGE_OUT`) numa etapa **diferente** de X, **Then** o `/api/scan` **rejeita com 403** e mensagem clara ("Você não está atribuído a este setor").
- [ ] **AC3:** **Given** o mesmo operador bipa **no seu setor X**, **When** válido, **Then** a bipagem ocorre normalmente.
- [ ] **AC4:** **Given** um usuário **ADMIN/gerente**, **When** bipa em qualquer setor, **Then** **não é bloqueado** (isento do enforcement) — configurável por permissão.
- [ ] **AC5:** **Given** um operador **sem nenhum setor atribuído**, **When** tenta bipar, **Then** é **bloqueado (403)** em qualquer setor (decisão confirmada: bloquear tudo).
- [ ] **AC6:** **Given** a atribuição de setor, **When** existe, **Then** é **coerente com a meta individual** (`user_targets`) — a mesma etapa serve para meta e para enforcement (evitar dois vínculos divergentes).
- [ ] **AC7:** `lint`, `tsc`, `build` passam; RLS/tenant preservados; sem regressão de scan para quem está no setor certo.

## Escopo

**IN:**
- **Dado (@data-engineer):** modelo do vínculo usuário→setor.
  - *Default (1 setor/pessoa):* reaproveitar `user_targets.stage_id` (já existe) como o setor do usuário — sem tabela nova.
  - *Se "vários setores/pessoa":* tabela nova `user_stages` (user_id, stage_id, tenant_id) + RLS + índices.
- **Backend (@dev):** enforcement em `src/app/api/scan/route.ts` — resolver o(s) setor(es) do usuário e comparar com `stage_id`; 403 se não permitido; isenção para ADMIN/gerente por permissão.
- **UI admin (@dev + @ux):** tela para atribuir setor por colaborador (provável em `/team` ou `/settings`), com `can(user, "users:manage")`/`settings:manage`.

**OUT:**
- Não altera o cálculo de meta (isso é 9.2/9.3).
- Não redesenha RBAC (reusa `effective-permissions.ts`).

## Dependências
- RBAC dinâmico (`effective-permissions.ts`) e `user_targets` já existentes.
- Recomendado implementar **após** 9.2/9.3 (evita retrabalho de meta) — mas é independente tecnicamente.

## Decisões de produto (CONFIRMADAS pelo usuário)
1. ✅ **Vários setores por pessoa** — o admin marca 1+ setores por colaborador. **Impacto:** exige **tabela nova `user_stages`** (user_id, stage_id, tenant_id) + RLS + índices (→ @data-engineer). O enforcement no scan aceita o `stage_id` se estiver no conjunto de setores do usuário.
2. ✅ **Bloquear tudo sem setor** — usuário sem nenhum setor atribuído não bipa em lugar nenhum (403).
3. ✅ **Isenção: ADMIN + gerente** — ambos bipam qualquer setor; operadores restritos aos seus setores. Implementar via permissão (ex.: `scan:any-sector`) para ficar configurável no RBAC.

> ⚠️ A escolha "vários setores" descarta reaproveitar `user_targets` como fonte única — a atribuição de setores passa a ser a nova `user_stages` (a `user_targets` continua só para a meta individual).

## Notas para o Dev
- Mensagem de 403 clara e amigável no app de scan (chão de fábrica) — não só JSON cru.
- Cuidado com o custo: resolver o setor do usuário 1× por request (cache leve por sessão se necessário).
