## Descrição

Como operador ou gerente, preciso registrar defeitos encontrados em um lote durante a produção e encaminhá-lo para retrabalho, mantendo rastreabilidade completa do problema e da resolução.

**Contexto:** A tabela `defect_records` já existe no schema com campos completos (quantity, defect_type, severity, description, detected_by, resolved_by, status). O enum `DefectType` tem COSTURA, TECIDO, AVIAMENTO, OUTRO. O enum `LotStatus` NÃO inclui status de retrabalho. A tela de bipagem (`/scan`) existe e funciona. Esta story integra o registro de defeitos à tela de bipagem, adiciona `IN_REWORK` ao `LotStatus`, cria a tela de listagem/resolução de retrabalhos, e adiciona um relatório básico.

## Critérios de Aceitação

- [ ] **AC1:** Na tela de bipagem (`/scan`), após bipar um lote com sucesso, botão "Reportar Defeito" aparece no card de resultado. Ao clicar, abre modal de registro
- [ ] **AC2:** Modal de defeito: tipo (dropdown com valores do enum `DefectType`: Costura, Tecido, Aviamento, Outro), severidade (dropdown: Leve, Médio, Grave), quantidade defeituosa (number), descrição (texto livre). Submit via `POST /api/defects`
- [ ] **AC3:** Ao registrar defeito, lote muda status para `IN_REWORK` automaticamente (via API). Campo `previous_stage_id` é salvo no defect_record para saber para onde retornar
- [ ] **AC4:** Tela `/rework` lista lotes em retrabalho. Filtros: tipo de defeito, OP, período. Acessível para `operador` e `gerente`
- [ ] **AC5:** Ação "Concluir Retrabalho" na tela `/rework`: atualiza `defect_records.status` para `RESOLVED`, `resolved_by`, `resolved_at`, e retorna lote ao status/etapa anterior (`previous_stage_id`)
- [ ] **AC6:** Aba "Relatório" na tela `/rework`: tabela com defeitos agrupados por tipo e por OP, com totais, filtro por período
- [ ] **AC7:** Build e typecheck passam: `tsc --noEmit` + `next build` sem erros

## Riscos

| Risco | Impacto | Mitigação |
|-------|---------|-----------|
| Migração do enum `LotStatus` pode afetar queries existentes | Lotes existentes não afetados (novo valor adicionado, não removido) | Adicionar valor ao enum é aditivo, não breaking |
| Campo `previous_stage_id` precisa ser nullable no defect_records | Defeitos existentes (portal de facções) não têm esse campo | Campo nullable, default null — não afeta registros existentes |
| Tela de bipagem já é complexa (~300 linhas) | Modal pode adicionar complexidade | Extrair modal para componente separado |

### Schema Existente — USAR, NÃO RECRIAR

A tabela `defect_records` JÁ EXISTE com o seguinte schema (Prisma → Supabase):

```
defect_records:
  id              UUID (PK, auto)
  lot_id          UUID (FK → lots)
  shipment_id     UUID? (FK → faction_shipments, nullable — usado pelo portal de facções)
  quantity         Int (default 1)
  defect_type      DefectType (enum: COSTURA, TECIDO, AVIAMENTO, OUTRO)
  severity         DefectSeverity (enum: LEVE, MEDIO, GRAVE)
  description      String?
  photo_url        String? (não usar nesta story)
  detected_by      UUID (FK → profiles)
  detected_at      DateTime (auto)
  resolved_by      UUID? (FK → profiles)
  resolved_at      DateTime?
  resolved_quantity Int (default 0)
  discarded_quantity Int (default 0)
  resolution       String?
  status           String (default "PENDING")
```

**NÃO criar tabela `rework_records`** — usar `defect_records` diretamente.

### Migração Necessária

**1. Adicionar `IN_REWORK` ao enum `LotStatus`:**
```sql
ALTER TYPE "LotStatus" ADD VALUE 'IN_REWORK';
```

**2. Adicionar `previous_stage_id` à tabela `defect_records`:**
```sql
ALTER TABLE defect_records ADD COLUMN previous_stage_id UUID REFERENCES stages(id);
```

**3. Atualizar Prisma schema** para refletir as mudanças.
