## Descrição

Reformula o sistema de metas para refletir a operação real (feedback da Karen):

- **Coeficiente por (referência × etapa):** hoje cada referência tem 1 coeficiente único. Precisa de um coeficiente por etapa. Ex: ref 1027 → Corte=1, Travete=20, Produção=2, Embalagem=1; e varia por referência (1006 na produção=1).
- **Meta diária por SETOR com unidade:** hoje há 1 meta global ("500 peças"). Precisa de meta por setor/etapa com unidade própria: Produção=180 conjuntos, Travete=2.500 travetadas, Corte=N cortes, Embalagem=N.
- **Override individual por usuário:** além da meta do setor, permitir meta própria por funcionário (decisão do dono: "os dois"). O usuário herda a do setor, salvo override individual.
- **Dashboard personalizado:** cada usuário vê a meta e o progresso do SEU setor, na unidade certa, medido pelas SUAS bipagens × coeficiente da etapa para a referência de cada lote. Admin vê o total global (8.19) também.
- **Edição admin-only:** matriz de coeficientes e metas editáveis apenas pelo administrativo (`settings:manage`).

## Decisões do dono (2026-06-19)

1. Granularidade: meta por **setor** (base) **+** override **individual** por usuário.
2. Dashboard: **personalizado por setor** para o operador; total global mantido para o admin.
3. Hotfix de persistência sai antes (Story 8.20).

## Modelo de Dados (concreto)

```sql
-- 1) Matriz coeficiente por referência × etapa
reference_stage_targets (
  id uuid pk, tenant_id uuid, reference text, stage_id uuid,
  coefficient numeric(6,2) not null default 1.0,
  unique(tenant_id, reference, stage_id)
)

-- 2) Meta diária por SETOR (= etapa) com unidade
sector_targets (
  id uuid pk, tenant_id uuid, stage_id uuid,
  daily_target integer not null, unit text,            -- ex: "travetadas", "conjuntos", "cortes"
  unique(tenant_id, stage_id)
)

-- 3) Override por USUÁRIO (decisão "os dois") — carrega a etapa do usuário
user_targets (
  id uuid pk, tenant_id uuid, user_id uuid, stage_id uuid,
  daily_target integer, unit text,                     -- nulos herdam do sector_target da etapa
  unique(tenant_id, user_id)
)
```
RLS: SELECT tenant-scoped; INSERT/UPDATE/DELETE tenant-scoped (gate admin na API via `settings:manage`). Mesmo padrão das tabelas irmãs + a policy de UPDATE corrigida na 8.20.

## Decisão de mapeamento usuário→etapa (architect)

O usuário é ligado a uma etapa por **atribuição explícita do admin** em `user_targets.stage_id` (ex: "Maria → Travete, 2500 travetadas"; "Andiara → Produção, 180 conjuntos"). É o mais robusto e cobre exatamente os exemplos da Karen. Fallback: se o usuário não tiver `user_targets`, tenta casar `profiles.sector` com `stages.name` e usa o `sector_targets` da etapa.

## Cálculo da meta personalizada (dashboard do operador)

```
progresso = Σ (lot.quantity × coefficient[lot.reference][etapa_do_usuário])
            sobre os STAGE_IN do usuário na sua etapa, no período
meta      = user_targets.daily_target  (se houver)  senão  sector_targets[etapa].daily_target
unidade   = user_targets.unit  ||  sector_targets[etapa].unit
```
Ex (travete): 150 conjuntos × coef 20 = 3000 travetadas vs meta 2500 → 120%.

## Notas Técnicas / Riscos

- **Relação com 8.19:** 8.19 mede produção global = peças na entrada do estoque. Esta story adiciona a visão **por setor** (produtividade medida na etapa do usuário). Ambos coexistem; o operador vê a do setor, o admin vê as duas.
- **Mapeamento setor↔etapa:** definir como `profiles.sector` casa com `stages` (ex: sector="PRODUCAO" → stage PRODUCAO). Pode exigir normalização dos valores de `sector`.
- **Unidade é rótulo livre** por setor (Fase 4).
- Depende da 8.20 (persistência de settings) para qualquer config gravar.
