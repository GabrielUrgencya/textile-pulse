## Descricao

Como administrador e operador, preciso de um sistema de autenticacao seguro com duas modalidades: email/senha para admin (via Supabase Auth) e PIN rapido para operadores de chao de fabrica, com rate limiting para prevenir brute force.

## Criterios de Aceitacao

- [ ] **AC1:** Login admin via Supabase Auth (email/senha) funcional no endpoint `/api/auth/login`
- [ ] **AC2:** Login operador via PIN no endpoint `/api/auth/pin` — valida PIN com bcrypt
- [ ] **AC3:** Rate limiting no `/api/auth/pin`: 5 tentativas por IP+tenant em janela de 15 min
- [ ] **AC4:** Apos 5 falhas: bloqueio 15 min, resposta HTTP 429
- [ ] **AC5:** Header `X-RateLimit-Remaining` presente nas respostas do `/api/auth/pin`
- [ ] **AC6:** Rate limiting implementado em memoria (`Map<string, {count, expiry}>`)
- [ ] **AC7:** Middleware de autenticacao valida sessao Supabase em todas as API Routes protegidas
- [ ] **AC8:** Supabase client server-side criado com `createServerClient()` do `@supabase/ssr`
- [ ] **AC9:** `src/lib/prisma.ts` removido do runtime da aplicacao (nao importado em nenhuma API Route)
- [ ] **AC10:** Logout funcional em `/api/auth/logout`

## Escopo

**IN:**
- Endpoint `/api/auth/login` (email/senha via Supabase Auth)
- Endpoint `/api/auth/pin` (PIN bcrypt com rate limiting)
- Endpoint `/api/auth/logout`
- Middleware de autenticacao para API Routes
- Supabase server client (`createServerClient`)
- Rate limiting em memoria
- Remocao do Prisma do runtime

**OUT:**
- OAuth / login social
- Reset de senha (usar Supabase built-in)
- Rate limiting distribuido (Redis — Fase 2+)
- Refresh token automatico (Supabase gerencia)
- Frontend de login (ja existe no Lovable)

## Notas Tecnicas

- **Item 2 (v2.1):** PIN ja esta hasheado com bcrypt no seed (`bcrypt.hash("1234", 10)`). NAO migrar para argon2id.
- **Item 3 (v2.1):** Rate limiting em memoria e suficiente para Fase 1. Chave: `${ip}:${tenantId}`. Se necessario, migrar para Upstash Redis na Fase 2+.
- **Item 4 (v2.1 — ADR-003):** Supabase client autenticado e a UNICA camada de acesso ao banco em runtime. Prisma apenas para `generate` e `migrate`.
- **Supabase SSR:** Usar `createServerClient()` do `@supabase/ssr` para criar client autenticado nas API Routes.
- **Fluxo PIN:**
  1. Operador envia `{ tenantId, pin }` para `/api/auth/pin`
  2. Server busca profiles do tenant com Supabase client
  3. Compara PIN com bcrypt.compare() contra cada profile
  4. Se match, cria sessao Supabase para o operador
  5. Se falha, incrementa contador de rate limiting
- **Verificacao AC9:** Rodar `grep -r "prisma" src/app/api/` deve retornar vazio
- **Source:** `docs/architecture/ARCHITECTURE-REVIEW-v2.1.md` items 2, 3, 4
